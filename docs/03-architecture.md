# 03. Архитектура и этапы реализации

Документ отвечает на вопросы «на чём делаем», «как устроены данные» и «сколько это стоит
по шагам». Он написан под конкретную ситуацию: сейчас в системе **нет Node.js**, поэтому
Этап 1 закрыт статическим прототипом, а продакшен-стек разворачивается на Этапе 2,
когда появится окружение.

## 1. Что есть сейчас (Этап 1)

| Слой | Реализация | Ограничения |
| --- | --- | --- |
| Разметка | 2 статических файла: `prototype/index.html`, `prototype/catalog.html` | без сборщика, без шаблонизатора |
| Стили | `tokens.css` (дизайн-токены) + `site.css` (компоненты, адаптив, печать) | один CSS-файл ~1450 строк, каскад без CSS-in-JS |
| Логика | `assets/js/data.js` (демо-данные), `icons.js` (SVG-спрайт из 18 иконок), `app.js` (вся интерактивность) | vanilla ES5-совместимый JS, IIFE, без модулей |
| Данные | массив из 9 демо-объектов в `data.js` | правятся только в коде |
| Формы | валидация + честное сообщение «данные не отправлены» | бэкенда нет |
| Избранное | `localStorage`, ключ `hz_favorites_v1` | живёт в одном браузере |
| Запуск | двойной клик по HTML, `file://` или любой статический хостинг | без серверных роутов |

Прототип сознательно сделан так, чтобы его можно было открыть без установки чего-либо:
это инструмент согласования дизайна, а не продакшен-код. Перенос в Next.js идёт
по компонентам, а не «переписыванием с нуля»: классы и токены сохраняются.

## 2. Стек продакшена (Этап 2+)

| Задача | Выбор | Почему он | Альтернативы и почему нет |
| --- | --- | --- | --- |
| Фреймворк | **Next.js 15 (App Router) + TypeScript** | SSR/ISR для SEO-страниц объектов, стриминг, серверные экшены для форм, один проект на сайт и админку | Astro — слабее в интерактиве кабинета; Nuxt — нет смысла, экосистема РФ-хостинга чаще под Next |
| Стили | **CSS-переменные из `tokens.css` + CSS Modules** (Tailwind опционально) | токены уже написаны, дизайн не зависит от утилит-классов; нет «классового ада» | Tailwind-only — потеряем готовые токены и читаемость компонентов |
| БД | **PostgreSQL 16 + Prisma ORM** | строгая типизация, миграции, простые связи объект↔фото↔район, поиск по фильтрам | SQLite — нет конкурентных записей и бэкапов на хостинге; MongoDB — данные строго реляционные |
| Файлы | **S3-совместимое хранилище** (Yandex Object Storage / Timeweb S3) | фото объектов тяжёлые, их нельзя держать в git и на диске приложения | хранение в БД — дорого и медленно |
| Изображения | `next/image` + пресеты 400/800/1600, AVIF/WebP | LCP и трафик; автоматическая генерация размеров | ручные `<img>` — снова ручная оптимизация |
| Аутентификация | **Auth.js (NextAuth) Credentials + bcrypt**, сессии в БД | нужны всего две роли, без соцвходов; клиенту вход не обязателен | Clerk/Auth0 — внешний сервис и оплата в валюте |
| Почта | **Resend** (или SMTP Яндекс 360) | уведомления о заявках и ответы клиенту | собственный SMTP — репутация и спам-фильтры |
| Telegram | **Bot API** (webhook) + канал | заявки в личку Ксении, автопубликация в канал | ручное копирование — теряются заявки |
| Карта | **Яндекс.Карты JS API** (ленивая загрузка) | точные адреса и пробки в РФ, привычный интерфейс | Google Maps — недоступность и оплата |
| Валидация | **Zod** схемы, общие для клиента и сервера | одна схема на форму и API | ручные проверки — расхождения |
| Деплой | **Vercel** либо **Timeweb Cloud** (Docker) | Vercel быстрее стартовать; Timeweb — данные в РФ и оплата в рублях | shared-хостинг — нет Node |
| Аналитика | **Яндекс.Метрика** (цели) | бесплатно, привычные отчёты | Google Analytics — вопросы доступности |

**Требования к окружению Этапа 2:** Node.js LTS 20/22 + npm, Git, доступ к PostgreSQL
(локально Docker или облако). Сейчас в системе Node нет — это первый шаг перед разработкой.

## 4. Модель данных

```prisma
model User {
  id           String   @id @default(cuid())
  email        String   @unique
  passwordHash String
  name         String
  role         Role     @default(CLIENT)   // CLIENT | ADMIN
  phone        String?
  createdAt    DateTime @default(now())
  favorites    Favorite[]
  leads        Lead[]
}

model City {
  id        String     @id @default(cuid())
  slug      String     @unique        // ekb
  name      String                    // Екатеринбург
  districts District[]
  listings  Listing[]
}

model District {
  id       String  @id @default(cuid())
  slug     String
  name     String
  cityId   String
  city     City    @relation(fields: [cityId], references: [id])
  listings Listing[]
  @@unique([cityId, slug])
}

model Listing {
  id          String        @id @default(cuid())
  slug        String        @unique
  title       String
  description String
  type        ListingType                     // APARTMENT | HOUSE | LAND | COMMERCIAL
  status      ListingStatus @default(DRAFT)   // DRAFT | MODERATION | ACTIVE | RESERVED | SOLD | ARCHIVED
  cityId      String
  districtId  String?
  address     String?                         // точный адрес только для ACTIVE
  rooms       Int?
  area        Decimal       @db.Decimal(7, 2)
  plot        Decimal?      @db.Decimal(8, 2)
  floor       Int?
  floors      Int?
  price       Int                             // рубли, целое
  pricePerM2  Int?                            // считается на сохранении
  isDemo      Boolean       @default(false)
  publishedAt DateTime?
  updatedAt   DateTime      @updatedAt
  createdAt   DateTime      @default(now())
  photos      ListingPhoto[]
  favorites   Favorite[]
  leads       Lead[]
  @@index([status, type, cityId, price])
  @@index([districtId, rooms])
}

model ListingPhoto {
  id        String  @id @default(cuid())
  listingId String
  key       String            // ключ в S3
  width     Int
  height    Int
  blurHash  String?
  sort      Int     @default(0)
  isCover   Boolean @default(false)
  listing   Listing @relation(fields: [listingId], references: [id], onDelete: Cascade)
}

model Favorite {
  userId    String
  listingId String
  createdAt DateTime @default(now())
  @@id([userId, listingId])
}

model Lead {
  id        String   @id @default(cuid())
  kind      LeadKind                 // CONSULT | SELL | CALLBACK
  name      String
  phone     String
  message   String?
  source    String                   // hero | sell | cta | object
  listingId String?
  consentAt DateTime
  ipHash    String?                  // без хранения IP в открытом виде
  status    LeadStatus @default(NEW) // NEW | IN_WORK | DONE | SPAM
  createdAt DateTime @default(now())
  @@index([status, createdAt])
}

model Review {
  id         String       @id @default(cuid())
  authorName String
  text       String
  rating     Int          // 1..5
  dealType   String?
  status     ReviewStatus @default(MODERATION) // MODERATION | PUBLISHED | REJECTED
  publishedAt DateTime?
  createdAt  DateTime     @default(now())
}

model Post {
  id          String    @id @default(cuid())
  slug        String    @unique
  title       String
  excerpt     String
  body        String              // MDX
  coverKey    String?
  status      PostStatus @default(DRAFT)
  publishedAt DateTime?
  tgMessageId Int?                // если опубликован в канале
}
```

**Правила, зашитые в модель:**
1. `status` вместо удаления — объекты не пропадают из выдачи «продан», а получают `SOLD`
   и плашку; удаление — только для ошибочно созданных.
2. `isDemo` — единственный способ показать демонстрационный объект на живом сайте;
   по умолчанию `false`, в сиде `true` только для тестовых записей.
3. `address` скрывается для неопубликованных объектов: адрес не должен утечь до модерации.
4. `Lead.ipHash` — sha256(ip + соль): защита от спама без нарушения приватности.

## 5. API и серверные операции

| Метод и путь | Назначение | Валидация | Ответ |
| --- | --- | --- | --- |
| `GET /api/listings` | список для каталога и бесконечной подгрузки | zod `filterSchema` (тип, город, район, комнаты, цена, площадь, этаж, sort, page) | `{ items, total, page, pageSize }` |
| `POST /api/leads` | заявка с любой формы | `leadSchema`: имя ≥2 символа, телефон по маске, `consent === true`, honeypot пуст | `201 { id }`, `400` с полями, `429` при лимите |
| `POST /api/reviews` | отзыв (только после сделки, по коду) | текст 40–1200 знаков, рейтинг 1–5 | `202` — уходит на модерацию |
| `POST /api/favorites` / `DELETE` | избранное авторизованного клиента | сессия обязательна | `204` |
| `POST /api/uploads` | подпись прямой загрузки в S3 | только `ADMIN`, mime ∈ jpeg/png/webp, ≤8 МБ | `{ url, fields, key }` |
| `POST /api/telegram/webhook` | приём апдейтов бота | секретный заголовок `X-Telegram-Bot-Api-Secret-Token` | `200` всегда, обработка в очереди |

Правила API:
1. Никаких «успехов без записи»: ответ `201` только после сохранения в БД и постановки
   уведомления в очередь.
2. Все ошибки — единый формат `{ error: { code, message, fields? } }`, код из фиксированного
   списка (`VALIDATION`, `RATE_LIMIT`, `UNAUTHORIZED`, `NOT_FOUND`, `CONFLICT`).
3. Список объектов кэшируется: `revalidateTag('listings')` после любого изменения в админке.
4. Счётчик «Найдено N» отдаёт сервер — иначе пагинация и SEO-сниппеты расходятся.

| --- | --- | --- | --- |
| Смотреть каталог и объекты | да | да | да |
| Избранное | в браузере (`localStorage`) | в БД, синхронизируется | да |
| Оставить заявку | да | да | — |
| Видеть свои заявки | нет | да | все |
| Создавать и править объекты | нет | нет | да |
| Публиковать (статус `ACTIVE`) | нет | нет | да |
| Модерировать отзывы | нет | нет | да |
| Публиковать в Telegram-канал | нет | нет | да |

`requireAdmin()` — серверный guard в каждом админ-экшене и route handler;
скрытая кнопка в UI защитой не считается. Вход — по e-mail и паролю, сброс пароля по ссылке
на 30 минут, обязательный 2FA-код в Telegram для `ADMIN` (Этап 4).

## 7. Фотографии объектов

1. Загрузка идёт напрямую в S3 по подписанной ссылке — сервер не проксирует мегабайты.
2. При загрузке снимается EXIF (включая геометки), генерируются 400/800/1600 px в WebP/AVIF,
   считается blurhash для плавного появления.
3. Порядок и обложка задаются в админке перетаскиванием; первая фотография — обложка карточки.
4. Минимум для публикации: 4 фото, из них одно — фасад или вид из окна. Объект без фото
   нельзя перевести в `ACTIVE` (валидация на сервере, не только в UI).
5. Плейсхолдеры из прототипа (`assets/img/listing-*.svg`) остаются только для демо-режима
   и для «фото готовится».

## 8. Формы, антиспам и персональные данные

- Поля: `name` (2–60 знаков), `phone` (маска `+7 (999) 123-45-67`, 11 цифр), `message` ≤1000,
  `consent` (чекбокс, обязателен), honeypot-поле `company` (должно быть пустым), время
  заполнения ≥2 с.
- Лимиты: 3 заявки с одного `ipHash` в час, 1 заявка на телефон в 10 минут, общий потолок
  20/час на сайт. Ответ — `429` с человеческим текстом «слишком много попыток».
- Согласие: дата и версия политики сохраняются в `Lead.consentAt` + `consentVersion`.
  Без политики ПД (Этап 2) форма на живом сайте не запускается.
- Данные не уходят в сторонние трекеры: номера телефонов и тексты заявок не передаются
  в аналитику, только факт события.

## 9. Интеграция с Telegram (Этап 4)

**Что делает бот — две независимые функции, их можно внедрять по очереди.**

1. **Уведомления о заявках.** `POST /api/leads` → сообщение в личный чат Ксении:
   тип, имя, телефон (кликабельный), текст, объект (если есть), источник, время.
   Кнопки: «Взял в работу» (меняет `Lead.status` на `IN_WORK`), «Спам». Если отправка
   не удалась — заявка уже в БД, повтор из очереди; потеря заявки невозможна.
2. **Публикация в канал.** Из админки: «Опубликовать в Telegram» → фото + подпись
   (заголовок, цена, район, площадь) + ссылка на объект, `Post.tgMessageId` сохраняется.
   Правка объекта не перепубликует пост автоматически — только по кнопке (чтобы не спамить).

**Чего бот не делает:** не принимает заявки вместо сайта, не хранит переписку,
не является единственным каналом уведомлений (дублирующее письмо на e-mail).

**Настройка:** @BotFather → токен в `TELEGRAM_BOT_TOKEN`, чат Ксении в `TELEGRAM_ADMIN_CHAT_ID`,
канал в `TELEGRAM_CHANNEL_ID`, вебхук с `secret_token`. Токены — только в переменных
окружения; в репозиторий и в клиентский код не попадают.

## 10. SEO и разметка

| Элемент | Правило |
| --- | --- |
| `<title>` | `Объект: 2-комнатная квартира, 62 м², Академический — 9 850 000 ₽` (до 60 знаков в видимой части) |
| `description` | 120–160 знаков, без «купить недорого», с районом и ценой |
| `canonical` | на каждой странице; фильтры каталога канонизируются на чистый `/catalog` |
| OG/Twitter | обложка 1200×630, фото объекта для карточки |
| JSON-LD | `RealEstateListing` (объект), `Person` (Ксения), `BreadcrumbList`, `Article` (блог), `Organization`/`LocalBusiness` на контактах |
| `sitemap.xml` | генерируется из БД: главная, каталог, все `ACTIVE` объекты, статьи, лендинги |
| `robots.txt` | закрыты `/admin`, `/api`, `/login`, `/account`; sitemap указан |
| 404 | человеческий текст + поиск по каталогу + 6 объектов из той же категории |
| Переезд | при смене slug — 301, старые адреса хранятся в таблице `Redirect` |

Ограничение: **никакой разметки, обещающей то, чего нет** — если объект демонстрационный,
он не попадает в sitemap и получает `noindex`. Отзывы размечаются `Review`-схемой только
после реальной модерации.

## 11. Производительность (бюджеты)

| Метрика | Цель | Как достигаем |
| --- | --- | --- |
| LCP (мобильный) | ≤2,5 с | обложка объекта через `next/image` с `priority`, шрифты с `display: swap` и preload двух начертаний |
| CLS | ≤0,05 | фиксированные `aspect-ratio` у медиа, скелетоны той же высоты |
| INP | ≤200 мс | минимум JS на первом экране, фильтры без полной перерисовки страницы |
| Вес первой загрузки | ≤180 КБ JS + ≤60 КБ CSS (gzip) | серверные компоненты, разделение бандлов по маршрутам |
| Изображения | AVIF/WebP, ≤200 КБ на обложку | пресеты 400/800/1600, `sizes` под сетку карточек |
| Каталог | первый экран сервером, подгрузка по 12 | ISR/кэш тега `listings`, курсорная пагинация |

Шрифты: два начертания с кириллицей, самостоятельный хостинг (без Google Fonts) —
и быстрее, и без передачи IP посетителей третьей стороне.

## 12. Безопасность и эксплуатация

- Валидация на сервере для всех входов (Zod), параметризованные запросы через Prisma.
- Заголовки: CSP (без `unsafe-inline` для скриптов), `X-Content-Type-Options`, `Referrer-Policy`,
  `Permissions-Policy`, HSTS на проде.
- Секреты только в переменных окружения; `.env` в `.gitignore`; ротация токена бота при утечке.
- Пароли — bcrypt (cost 12), сессии в БД с отзывом, ограничение попыток входа (5 за 15 минут).
- Бэкапы PostgreSQL: ежедневный дамп + хранение 14 дней; раз в месяц — проверка восстановления.
- Логи: заявки, ошибки, вход в админку. Персональные данные в логи не пишутся.
- Мониторинг: uptime-проверка раз в минуту + оповещение в Telegram при 5xx.

## 15. Риски и открытые вопросы

| Риск | Влияние | Что делаем |
| --- | --- | --- |
| Нет реальных фото и контактов | сайт нельзя запустить | чек-лист `docs/04`, до запуска — только демо-режим с явными пометками |
| Нет Node/окружения на машине | Этап 2 не стартует | установка Node LTS как первый шаг; прототип уже показывает дизайн |
| Объекты быстро устаревают | недостоверная выдача | статусы `ACTIVE/RESERVED/SOLD`, автопометка «проверено N дней назад», ручная ревизия раз в неделю |
| Юридические требования (152-ФЗ, реклама) | штрафы, блокировка | политика ПД и согласие до запуска форм; никаких обещаний доходности; пометка «реклама» при необходимости |
| Спам в заявках | потеря реальных обращений | honeypot + лимиты + ручная отметка «спам» |
| Один человек поддерживает сайт | всё встанет при болезни | админка простая, документация, бэкапы, второй контакт для доступа |
